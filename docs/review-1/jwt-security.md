## 1. Security Architecture Overview

VAYRO enforces a zero-trust, stateless authentication model across the entire distributed system. All requests crossing the API Gateway perimeter are authenticated via JSON Web Tokens (JWT) signed with HMAC-SHA256.

## 2. JSON Web Token (JWT) Anatomy

The JWT generated by `user-service` adheres strictly to standard RFC 7519 specifications:

### 2.1 Header
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 2.2 Payload (Claims)
```json
{
  "sub": "customer@vayro.com",
  "userId": "101",
  "email": "customer@vayro.com",
  "name": "Alex Mercer",
  "role": "USER",
  "iat": 1726963200,
  "exp": 1727049600
}
```

- `sub` (Subject): Customer email address.
- `userId`: Relational primary key of the user.
- `email`: Normalized lowercase email identifier.
- `name`: Full display name of the user.
- `role`: Authorization role (`USER` or `ADMIN`).
- `iat` (Issued At): UNIX timestamp of token generation.
- `exp` (Expiration): Expiration timestamp (Default: 24 Hours = 86,400,000 ms).

### 2.3 Signature
$$\text{Signature} = \text{HMAC-SHA256}\Big(\text{Base64Url}(\text{Header}) + "." + \text{Base64Url}(\text{Payload}), \ \text{JWT\_SECRET}\Big)$$

## 3. Password Security: BCrypt Hashing

User passwords are never stored in plaintext. VAYRO utilizes the **BCrypt adaptive hashing algorithm** with an internal cost factor (salt strength 10):

$$\text{Password Hash} = \text{BCrypt.hashpw}(\text{plaintextPassword}, \text{BCrypt.gensalt}(10))$$

### BCrypt Security Properties:
1. **Cryptographic Salting:** Generates a random 128-bit salt per password, preventing dictionary and precomputed rainbow table attacks.
2. **Computational Work Factor:** Key stretching algorithm forces intentional CPU latency during hashing, neutralizing brute-force cracking attempts.
3. **One-Way Function:** Computationally irreversible, ensuring credential privacy even in the event of database exfiltration.

## 4. Perimeter vs. Microservice Defense-in-Depth

VAYRO applies security at two distinct layers:

### 4.1 Layer 1 — Perimeter Security (API Gateway)
The `api-gateway` executes reactive `JwtReactiveAuthenticationManager` and `JwtServerAuthenticationConverter`:
- Validates token presence in `Authorization: Bearer <token>` header.
- Verifies cryptographic signature using `JWT_SECRET`.
- Validates expiration timestamp (`exp > now`).
- Rejects malformed, tampered, or expired tokens immediately with structured `401 UNAUTHORIZED` JSON responses.
- Rejects access to admin endpoints (`POST/PUT/DELETE /api/vehicles/**`) for `ROLE_USER` tokens with structured `403 FORBIDDEN` JSON responses.

### 4.2 Layer 2 — Microservice Security Context
Each downstream microservice (`user-service`, `booking-service`, `vehicle-service`) contains a localized `JwtAuthenticationFilter` or security context parser that reconstructs the `AuthenticatedUser` principal from the token or incoming header context.

## 6. Protection Against Privilege Escalation & Vulnerabilities

1. **Public Registration Role Hardcoding:**
   In `user-service/AuthService.java`, the registration routine explicitly sets `user.setRole(Role.USER)`. Public consumers cannot inject or request `ADMIN` role attributes during signup.
2. **Controlled Admin Bootstrap:**
   Administrative accounts cannot be registered via public APIs. Admin provisioning is strictly governed by `AdminInitializer.java` via secured server environment variables (`ADMIN_BOOTSTRAP_ENABLED=true`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`).
3. **Zero Hardcoded Secrets:**
   The cryptographic secret `JWT_SECRET` is never committed to version control. It is injected dynamically via runtime environment configuration across the Gateway and microservices.
4. **Stateless Scalability:**
   Because session state is contained entirely within the signed cryptographically verified JWT payload, any backend microservice or gateway instance can authenticate requests independently without querying a shared session cache or database.
