DriveEase — JWT Authentication

Secure Authentication and Authorization Architecture Specification

⚠️ Academic Architecture Disclaimer:
This page presents the planned JWT authentication and authorization architecture for the DriveEase microservice backend system. The current DriveEase React frontend uses client-side simulated authentication. The production backend JWT implementation will be completed during the backend deployment phase.

1. What is JWT (JSON Web Token)?

A JSON Web Token is an open standard (RFC 7519) for transmitting secure identity claims between client and server as a signed JSON object.

Header Part 1

Specifies the signing algorithm (e.g. RS256) and token type (JWT).

{"alg": "RS256", "typ": "JWT"}
Payload Part 2

Contains authenticated user claims (Subject ID, Role, Expiration).

{"sub": "usr_8912", "role": "CUSTOMER"}
Signature Part 3

Cryptographic hash proving token authenticity and integrity.

RS256(Header + Payload, PrivateKey)

2. Authentication vs. Authorization

Enforcing clear boundary separation between identity verification and permission checking.

AUTHENTICATION STEP 1

"Who are you?"

The process of verifying user identity credentials against the database hash during login.

  • Inputs: Email + Plaintext Password
  • Processing: Argon2id salted hash comparison
  • Output: Issuance of signed JWT Access & Refresh tokens
AUTHORIZATION STEP 2

"What are you allowed to do?"

The process of evaluating validated token role claims against requested API endpoints.

  • Inputs: Bearer JWT Access Token
  • Processing: Claims role validation (`CUSTOMER` vs `ADMIN`)
  • Output: `200 OK` (Proceed) or `403 Forbidden` (Blocked)

4. Access Token vs. Refresh Token

Dual-token architecture balancing high security with seamless user experience.

Access Token (Short-Lived) 15 MIN LIFETIME

Attached to every HTTP API request header. Carries user ID and role claims for stateless validation.

{
  "sub": "usr_891247",
  "role": "CUSTOMER",
  "name": "Jane Doe",
  "iss": "driveease-auth-service",
  "aud": "driveease-api-gateway",
  "iat": 1789056000,
  "exp": 1789056900,
  "jti": "jwt_b7a9c4d2"
}
Refresh Token (Long-Lived) 7 DAY ROTATION

Opaque token stored in HttpOnly SameSite cookies. Used to obtain new access tokens without re-logging in.

  • Rotation: Replaced with a new token on every refresh call.
  • Reuse Detection: If a refresh token is stolen and reused, all sessions are immediately revoked.
  • Revocation: Can be explicitly invalidated upon user logout.

6. Security Threats & Mitigations

Proactive defenses against common authentication vulnerabilities.

1. Token Theft

Short 15-min token life + HTTPS TLS 1.3 enforcement.

2. Refresh Theft

Refresh token rotation + reuse detection revocation.

3. Brute Force

Gateway rate limiting (5 login attempts/min per IP).

4. XSS & CSRF

HttpOnly, SameSite=Strict cookies + input sanitization.

7. Auth Service Boundary

Strict separation of Auth Service responsibilities within the microservices topology.

Auth Service OWNS:
  • ✓ Credential registration & email validation
  • ✓ Password hashing using Argon2id
  • ✓ Credential verification & login
  • ✓ JWT Access Token issuance & signing
  • ✓ Refresh Token rotation & revocation tracking
Auth Service DOES NOT OWN:
  • ✗ Vehicle specs, categories, or rates (Vehicle Svc)
  • ✗ Booking reservations or dates (Booking Svc)
  • ✗ Payment charges or invoices (Payment Svc)
  • ✗ Driving license KYC files (User Svc)
  • ✗ Email/SMS notification templates (Notification Svc)

9. Viva & Evaluation Quick Guide

Key questions a faculty evaluator may ask about JWT in DriveEase.

Q1: Explain JWT in 60 seconds.
"JWT is a compact, digitally signed JSON token used to securely represent authenticated identity between client and server. Upon login, Auth Service verifies the password hash and issues a short-lived Access Token (15 min) and a long-lived Refresh Token (7 days). The client sends this token with API requests. The API Gateway validates token signatures using public keys statelessly without querying the database, checking both identity and roles (CUSTOMER vs ADMIN)."
Q2: Why use JWT instead of traditional server session cookies?
JWT is stateless. Server microservices do not need to share a central session database to verify user identity, enabling seamless horizontal microservice scaling.
Q3: Why should passwords never be placed in a JWT payload?
JWT payloads are Base64URL encoded—not encrypted. Anyone who intercepts the token can read the claims payload. Passwords belong hashed in the database.
Q4: What is the difference between 401 Unauthorized and 403 Forbidden?
401 means authentication failed or token is missing/expired ("Who are you?"). 403 means identity is verified, but permissions are insufficient for the action ("What can you do?").
